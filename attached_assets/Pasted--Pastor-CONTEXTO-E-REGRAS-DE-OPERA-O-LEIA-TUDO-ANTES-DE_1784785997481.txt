1. POR QUE ESTE PROJETO ESTÁ SENDO REFEITO
═══════════════════════════════════════════════

A versão anterior falhou de quatro formas. Você precisa conhecê-las
porque são exatamente os erros que um agente de IA tende a repetir.

FALHA 1 — Duas stacks incompatíveis no mesmo repositório
  Havia React na raiz e Flutter em apps/mobile/. Nenhum agente decidiu
  isso; foi acontecendo. Nenhum dos dois funcionava.

FALHA 2 — Simulação apresentada como implementação  ← A MAIS GRAVE
  A tela exibia "Status Supabase: Conectado (Ativo)" como texto fixo em
  HTML. As feature flags vinham de um array escrito à mão no código.
  O botão "Testar endpoint" chamava setTimeout(400ms) e devolvia um
  objeto inventado. Não existia UMA linha de @supabase/supabase-js
  no projeto inteiro. O app PARECIA pronto e não fazia absolutamente nada.

FALHA 3 — Quebra silenciosa
  Um controller era instanciado sem sua dependência obrigatória, caía
  num bloco else e reportava "status: ready". A cadeia de código real
  existia, compilava, passava nos testes, e nunca era chamada.

FALHA 4 — Perda de contexto entre sessões
  Quem escreveu o SQL não era quem escreveu o cliente. Faltava uma
  extensão do banco, e ninguém percebeu até 16 testes falharem juntos.

Total auditado: 72 defeitos. Todos os 72 vieram de falta de regra,
não de falta de habilidade técnica.

3. AS DEZ REGRAS INVIOLÁVEIS
═══════════════════════════════════════════════

R-01  NUNCA exiba dado inventado como se viesse do banco.
      Sem conexão real, mostre o estado de erro real.
      Mock existe apenas dentro de src/tests/.

R-02  NUNCA converta falha em sucesso.
      Proibido: catch vazio; catch que retorna estado "ok";
      valor default que mascara ausência de dado; dependência
      opcional que finge funcionar quando é nula.

R-03  NUNCA use allowedHosts: true no Vite.
      Expõe o dev server a DNS rebinding. Se o Replit bloquear,
      eu forneço o hostname exato e você adiciona SÓ aquele.

R-04  NUNCA crie policy RLS para service_role.
      service_role ignora RLS por definição; a policy nunca executa.
      Para acesso server-only, use apenas GRANT.

R-05  NUNCA crie uma tabela public.schema_migrations.
      O Supabase já mantém supabase_migrations.schema_migrations.
      Duplicar isso quebra o db push.

R-06  NUNCA use \i dentro de arquivo .sql.
      \i é metacomando do cliente psql, não é SQL.
      Todo SQL necessário fica dentro da própria migration.

R-07  NUNCA altere schema pelo SQL Editor do Supabase.
      Schema muda por arquivo em supabase/migrations/ + db push.
      O SQL Editor serve apenas para LER e conferir.

R-08  NUNCA edite uma migration já aplicada.
      Mudança de schema = migration NOVA, aditiva.

R-09  NUNCA fixe versões de pacote à mão no package.json.
      Deixe o npm resolver e o package-lock.json congelar.

R-10  NUNCA escreva secret em arquivo.
      Chaves vão na aba Secrets do Replit. O .env.example contém
      apenas placeholders. A chave sbp_ é token de ADMIN e nunca,
      em hipótese alguma, entra no repositório.
